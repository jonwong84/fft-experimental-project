# ADR 0005: Use MonoGame DesktopGL for the first Windows presentation host

- **Status:** Recommended for ZOD-025; no production host or dependency integrated by this spike.
- **Date / web verification:** 2026-10-22.
- **Scope:** Windows game presentation/input adapter. Editor UI selection, audio fidelity, video decoding and renderer compatibility implementation remain separate work.

## Context and decision

Choose **MonoGame.Framework.DesktopGL 3.8.6**, initially Windows x64, as the first host's window/graphics/input stack. Keep .NET **10.0.402** selection and game logic managed. Native SDL/OpenGL/audio libraries are platform implementation dependencies, not a port of the C reference or an exception allowing native gameplay simulation.

MonoGame supplies the modest game-host/render/input facilities this slice needs without requiring a new graphics framework. The versioned DesktopGL source targets net8.0 and uses SDL2/OpenGL; the current stable release is v3.8.6, source commit **`c610a529667336f63da323c6057274258727664b`**. Actual .NET 10 compatibility evidence is the isolated probe below, rather than interpreting NuGet's computed target-framework compatibility as a tested GPU result. [Versioned framework project](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/MonoGame.Framework/MonoGame.Framework.DesktopGL.csproj), [release](https://github.com/MonoGame/MonoGame/releases/tag/v3.8.6).

The [architecture overview](../architecture/overview.md) separates Zodiac facilities, the FFT framework and authored game content. This choice adds presentation to a future host/composition root; it puts no MonoGame types, windowing, input polling, graphics resources or timing into `Tessera.Engine`, `Zodiac.Framework` simulation or immutable definition contracts. A later reusable presentation adapter can be extracted when concrete reuse warrants it. Existing projects are not renamed. The editor need not use this game-loop/window model; decide its UI framework separately.

## Compared options

### MonoGame DesktopGL — selected

The versioned project includes SDL window, keyboard/mouse/gamepad backends, OpenGL graphics and OpenAL support. Its API includes texture upload, render targets, explicit sampling/blend/depth state and game-window resizing. This is enough to build a synthetic battle-view host without owning raw device/swap-chain/input backends. The judgment that it is the smallest useful fit is this ADR's inference, not a comparative performance measurement. [DesktopGL 3.8.6 source](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/MonoGame.Framework/MonoGame.Framework.DesktopGL.csproj).

### MonoGame WindowsDX — viable fallback, not selected

The 3.8.6 target is net8.0-windows with WinForms and SharpDX 4.2.0 packages, including Direct3D11 and XInput. Official packaging guidance still calls for the DirectX June 2010 runtime for WindowsDX audio/gamepads. It would fit a Windows-only host, but adds that legacy deployment prerequisite and a different input/window path without solving a demonstrated requirement here. This alternative was documentation/source-reviewed, **not built or run**. DesktopVK/WindowsDX12 are not needed to prove this first host; reconsider those backends after a concrete rendering/deployment need and their own validation. [Versioned WindowsDX project](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/MonoGame.Framework/MonoGame.Framework.WindowsDX.csproj), [official packaging guide](https://docs.monogame.net/articles/getting_started/packaging_games.html).

### FNA — capable XNA-compatible alternative, not selected

FNA's official setup describes SDL for windows/input, FNA3D for graphics, FAudio for audio and optional Theorafile for video, distributed as source projects and native fnalibs. Its upstream FAQ explicitly states it does not publish official NuGet packages; copying an unofficial package into this solution would not follow upstream's supported workflow. Documentation recommends .NET 8 for new projects. No FNA revision, native bundle or .NET 10 execution was tested in this spike; the cited current documentation is an observation dated above, not a pinned runtime baseline. [Official setup](https://raw.githubusercontent.com/FNA-XNA/docs/main/docs/1%3A-Setting-Up-FNA.md), [official FAQ](https://raw.githubusercontent.com/FNA-XNA/docs/main/docs/0%3A-FAQ.md).

FNA has the relevant XNA-style facilities, but its XNA preservation focus is not PS1 rendering equivalence. Vendoring/pinning its source/submodules and matching native bundles introduces additional dependency/deployment workflow here. Its README identifies Ms-PL plus differently licensed portions, and its shipping guide separately places fnalibs in the published application. Retain it as an alternative if testing finds a concrete MonoGame backend limitation. [Upstream README/license overview](https://github.com/FNA-XNA/FNA), [distribution guide](https://raw.githubusercontent.com/FNA-XNA/docs/main/docs/3%3A-Distributing-FNA-Games.md).

### Silk.NET 2.23.0 — lower-level fallback, not selected

Silk.NET offers managed native-API bindings plus Windowing/Input utilities. The current documented/released version is 2.23.0. Choosing it would provide direct control over OpenGL or Direct3D11, but we would also own batching, texture/material conventions, render-target lifecycle and more graphics backend plumbing. It does not itself provide a PS1 renderer. This is an engineering-effort inference from its binding-oriented API, not a claim that those features are impossible. No Silk.NET package was restored, built or run here. [Official documentation](https://dotnet.github.io/Silk.NET/docs/), [release](https://github.com/dotnet/Silk.NET/releases/tag/v2.23.0).

Its window API usefully distinguishes framebuffer size/resize from window size and exposes client-to-framebuffer conversion, making it a credible fallback if high-DPI control proves obstructed in the selected host. The Windowing package includes native GLFW/SDL backend dependencies; a managed binding is not a managed-only deployment. Silk.NET's own license is MIT; native dependencies have separate notices. [Versioned window interface](https://raw.githubusercontent.com/dotnet/Silk.NET/v2.23.0/src/Windowing/Silk.NET.Windowing.Common/Interfaces/IView.cs), [versioned project](https://raw.githubusercontent.com/dotnet/Silk.NET/v2.23.0/src/Windowing/Silk.NET.Windowing/Silk.NET.Windowing.csproj), [license](https://raw.githubusercontent.com/dotnet/Silk.NET/v2.23.0/LICENSE.md).

## Rendering fit and explicit limitations

**Prepared textures and palettes:** use `Texture2D.SetData` with deliberately prepared RGBA bytes for the first slice; direct file loading is available but should not bypass the repository's prepared/hash-verified content boundary. Initially expand indexed pixels on the CPU with explicit palette selection, preserving the original indexed data and transparency/semitransparency metadata separately. A GPU palette lookup shader can follow if palette animation/recolor upload cost warrants it. No hardware-native PS1 palette semantics are assumed. The probe's index-zero transparent example is invented data, not a decoding rule for every FFT image. [Texture2D API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.Texture2D.html).

**Pixel sampling:** choose point filtering and clamp for original-style sprite samples, and explicitly disable unwanted mipmaps. Prepared atlas padding and UV bounds must prevent neighboring regions bleeding. Replacement textures may select a separate validated sampling policy; changing visual resolution must not change logical sprite extents, map positions or simulation coordinates. No renderer should silently derive hit areas from replacement image pixel dimensions. The API provides those sampling controls; their correct application remains host/render tests. [SamplerState API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.SamplerState.html).

**Transparency and blending:** carry opaque, transparent and semitransparent classification through asset preparation. `BlendState` exposes source/destination factors and operations; its standard AlphaBlend assumes premultiplied source color, whereas NonPremultiplied uses source alpha. Do not feed arbitrary decoded bytes through an implicit premultiplication conversion. PS1 blend approximations require explicit compatible equations and masks/passes; one generic alpha value or the built-in Additive preset is not proof of equivalence. Per-texel mixed modes may need an effect plus ordered passes, and screen-dependent operations may need a separate render target. This is a proposed implementation strategy, not a traced FFT blend rule or an executed shader test. [BlendState API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.BlendState.html), [blend-state guide](https://docs.monogame.net/articles/getting_to_know/whatis/graphics/WhatIs_BlendState.html).

**Depth/order and camera:** use explicit presentation submissions with documented ordering keys; preserve the eventual source-traced primitive/billboard ordering rather than replacing it with automatic sorting or a z-buffer solely because the library supplies one. Depth-tested opaque geometry and depth-read-only transparent geometry are available choices; cutout fragments and semitransparent ordering require deliberate handling. Camera view/projection transforms are presentation-only: rotation, zoom and widescreen aspect cannot mutate fixed simulation positions. The no-window probe executes synthetic `Matrix` camera math; it does not render or establish the original camera. [DepthStencilState API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.DepthStencilState.html).

**Resolution, widescreen and 1080p:** keep three values distinct: logical presentation/camera dimensions, selected internal render-target resolution, and physical window/backbuffer pixels. A `RenderTarget2D` can render at chosen dimensions and composite into a letterboxed/aspect-correct output viewport. This supports a path to a 1920×1080 output and selectable internal resolution; it does not automatically make game UI/camera framing widescreen-correct. Preserve original-compatible framing as one policy and make expanded framing/replacement textures explicit options in ZOD-059/060. Recreate render targets and camera/input transforms on the appropriate resize/device events. No GPU allocation/performance result at 1080p is claimed. [RenderTarget2D API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.RenderTarget2D.html).

**Resize/high DPI:** `GameWindow` provides resizing and client-size events, but its SDL window handle is not a Win32 HWND. Do not cast it to an HWND for DPI calls. The selected version's SDL window implementation uses SDL size/event plumbing; verify actual backbuffer dimensions and coordinate mapping instead of assuming window coordinates always equal framebuffer pixels. SDL2 supports requesting per-monitor-v2 awareness **before video initialization** through `SDL_WINDOWS_DPI_AWARENESS`; it is an available adapter policy, not a claim MonoGame has configured it or that all coordinate paths are correct. Mixed-DPI monitor moves, resize/minimize/restore and mouse picking are mandatory next-host checks. [GameWindow API](https://docs.monogame.net/api/Microsoft.Xna.Framework.GameWindow.html), [versioned SDL window implementation](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/MonoGame.Framework/Platform/SDL/SDLGameWindow.cs), [SDL DPI hint](https://wiki.libsdl.org/SDL2/SDL_HINT_WINDOWS_DPI_AWARENESS).

## Input and diagnostics

The selected DesktopGL target contains SDL keyboard, mouse and gamepad implementations. `GamePad` supplies capabilities, state queries, dead-zone modes and vibration. This supports the required keyboard/mouse/controller adapter, but no physical controller, hotplug, remapping or focus behavior was tested here. ZOD-061 owns those features and device checks. [Versioned backend selection](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/MonoGame.Framework/MonoGame.Framework.DesktopGL.csproj), [GamePad API](https://docs.monogame.net/api/Microsoft.Xna.Framework.Input.GamePad.html).

Host input should translate physical snapshots/edges into named UI actions and validated battle commands. Keep camera/UI repeat timing outside deterministic turns. Mouse picking must invert the actual output viewport, letterboxing, DPI scale and camera transforms. On focus loss, clear transient pressed/repeat state; controller disconnect should not leave a held command. These are proposed adapter contracts, not completed behavior.

For ZOD-025, log backend/package version, native loading failure, selected graphics profile/adapter, window/client/backbuffer/internal-target dimensions and input-device connection changes. Report device creation failures clearly; do not mask them as asset failures. Provide a synthetic render-target capture mode for transparent edges, palette selection and ordered blending, with local captures under ignored `scratch/`. Normal simulation tests stay graphics-independent; presentation checks remain separate from deterministic replay. No graphics debugger, render-target capture or GPU validation was executed by this spike.

## Native deployment and licenses

The tested package lock resolves **MonoGame.Framework.DesktopGL 3.8.6**, **MonoGame.Library.SDL 2.32.10.2**, **MonoGame.Library.OpenAL 1.24.3.4**, and **NVorbis 0.10.4**. The restored output contains Windows x64 SDL2 and OpenAL native DLLs; runtime SDL version query reports **2.32.10**. Package revision suffixes are not the SDL runtime version. These files are part of the platform adapter deployment; no C toolchain is required to build the C# game against the packaged binaries. OpenGL still requires an appropriate installed graphics driver, untested here.

MonoGame's main license is **Ms-PL**, with additional MIT portions; retain its applicable notices. SDL2 uses the **zlib** license, NVorbis **MIT**, and OpenAL Soft carries **GNU Library GPL v2** copying terms in its distributed license. Include the exact native/managed component notices and corresponding-source/relinkability materials required by the actual distributed build; MonoGame's top-level license does not replace those dependencies' terms. Keep native libraries replaceable as separate files for the first deployment. This is a component inventory and packaging requirement, not a statement that a compiled game release has already satisfied distribution obligations. [MonoGame license](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.6/LICENSE.txt), [SDL license](https://github.com/libsdl-org/SDL/blob/release-2.32.10/LICENSE.txt), [NVorbis license](https://raw.githubusercontent.com/NVorbis/NVorbis/v0.10.4/LICENSE), [OpenAL Soft copying terms](https://raw.githubusercontent.com/kcat/openal-soft/1.24.3/COPYING).

Recommend a folder-based **win-x64 self-contained** publish for the first Windows host, retaining prepared assets and native runtime files. Do not introduce trimming, AOT or single-file bundling in the first slice: those are separate deployment tests, not prerequisites for this choice. Self-contained .NET does not remove GPU-driver or native-component requirements. Upstream describes self-contained publishing and separately notes WindowsDX's legacy redist; its general wording about no external dependencies must not be read as a tested hardware/driver guarantee. No publish, installer or clean-machine launch was executed here. [Official distribution guide](https://docs.monogame.net/articles/getting_started/packaging_games.html).

Documentation version caveat: the generic supported-platform guide still mentions older Windows baselines, while the current package README lists Windows 10 22H2+. Adopt the **versioned package's current Windows baseline** for the first validation matrix, not an untested older-OS promise. Actual probe OS identity is recorded below. [Package metadata/README](https://www.nuget.org/packages/MonoGame.Framework.DesktopGL/3.8.6).

## Actual experiment and reproducibility

The optional standalone [probe project](../../tools/rendering-spike/RenderingSpike.csproj), [source](../../tools/rendering-spike/Program.cs), [lock](../../tools/rendering-spike/packages.lock.json) and [instructions](../../tools/rendering-spike/README.md) are outside `Fft.sln`. Only this project opts out of central package versions; no solution/project/package settings were changed. Generated binaries/native files and NuGet caches are not committed.

Executed from the repository with its pinned SDK **10.0.402**:

```powershell
dotnet restore tools/rendering-spike/RenderingSpike.csproj --locked-mode
dotnet run --project tools/rendering-spike/RenderingSpike.csproj -c Release --no-restore
```

Both passed. Observed runtime **.NET 10.0.13**, OS description **Microsoft Windows 10.0.26200**, process architecture **X64**, managed assembly version **3.8.6+c610a529667336f63da323c6057274258727664b**. The program checks invented four-color CPU palette expansion, unbound point/clamp and custom blend state construction, and finite synthetic camera matrices. It compiles a never-called `Texture2D.SetData`/1920×1080 `RenderTarget2D` code path, verifying API compatibility only.

This project targets plain `net10.0`, with no Windows-specific reference pack, WinForms workload or Windows SDK dependency added. That is tested build compatibility for this probe, not a statement about every backend's tooling. MGCB/effect compilation was not run; a future custom shader pipeline must pin and validate its own build tools before entering CI. Those tools must stay outside the running game and headless simulation.

The native check loads the restored Windows x64 SDL DLL and calls `SDL_GetVersion` without `SDL_Init`, reporting **2.32.10**; upstream explicitly documents this query as safe before initialization. It unloads the DLL afterward. No `Game`, window, graphics device, SDL video/input subsystem, audio device, real controller or game asset is opened. [SDL_GetVersion contract](https://wiki.libsdl.org/SDL2/SDL_GetVersion).

Consequently **window creation, texture upload execution, OpenGL support, 1080p frame performance, PS1 blend/depth correctness, physical input, resize and DPI behavior remain untested**. No visible/manual validation is claimed. A live window experiment was not necessary to choose between the reviewed host responsibilities; ZOD-025's synthetic host must perform those checks before claiming a working Windows battle view. If it exposes a genuine backend or DPI/palette limitation, revisit this ADR with evidence and the retained WindowsDX/Silk alternatives.

## Consequences and next bounded gate

Implementation follow-up (2026-10-23): ZOD-025 now integrates the exact package in `Fft.Client`.
[The host note](../development/windows-synthetic-host.md) records live window/GPU upload/readback,
maximize/restore, native close and snapshot-invariance checks. The no-window experiment above
remains historical evidence; physical keyboard/controller, mixed-DPI, forced-device-reset and
deployment checks are still limited as described in the follow-up.

ZOD-025 can add the selected host package at an exact reviewed version, with normal central-version/lock integration, and render invented tiles plus a synthetic palette sprite using prepared data. Its acceptance should record native graphics initialization, transparent/opaque pixels, sampling/order, input, resize/high-DPI mapping and reproducible Windows launch. Add no original game media to that proof. Keep client frame pacing and rendering resource lifetime outside CT/RNG/game simulation.

No full engine renderer abstraction, editor shell, native gameplay port, WotL/Lion War presentation policy, audio driver, video player or complete replacement-texture system is selected here. Those needs should drive their own bounded contracts and checks. This completes the stack-selection investigation with tested managed/native loading evidence and explicit limits; it does not complete the Windows host implementation.
