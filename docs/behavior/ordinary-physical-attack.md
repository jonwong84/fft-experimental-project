## Target selection and legality

`src/battle/target_panels.c::target_range_set_for_action` (954) rejects an out-of-range/absent actor and selects weapon targeting for Attack. `target_range_set_for_weapon` (785) clears panels, calls `target_range_calculate_weapon`, then clears the actor's own coordinate on both layers. Thus this branch does not include self-targeting.

`target_range_calculate_weapon` (379) selects the equipped weapon (with Frog/empty-hand fallbacks), reads its flags and invokes `target_range_calculate_strike_lunge` for striking/lunging flags. For STRIKING, `unit_get_effective_height` gives half-height 20 in this dry flat configuration; the four cardinal neighbors are marked only when their tile sample is inclusively in `[20-6,20+5] = [14,25]`. The helper `target_range_mark_tile_in_height_band` checks bounds and samples `2*height + half_height + 2*depth` on each layer. Untargetable tiles are removed; `target_range_set_flags` rejects blocked and cross-section tiles. No diagonal or two-tile target is in this striking range. These target samples are center/half-height samples, not movement exit-edge samples.

Range highlighting is not the complete final target test. `src/battle/action_preparation.c::target_calculate_action_tiles` calls `target_validate_for_weapon` for Attack. That function reads the actor's **stored** `action_command.target_position`; copying some local unit-target coordinates does not replace that stored target for this path. It finds the occupying unit, selects plain `target_validate_height_overlap` for this non-arc/non-direct/non-lunging weapon, clears targeted flags and marks only a returned unit. It can return **0 with no marked target**; zero is not a universal successful attack indication.

`unit_find_at_tile` (action_preparation, 1155) returns -2 for out-of-bounds coordinates/layer or collision tile, -1 when no eligible occupant exists. `target_find_unit_at_tile` supplies no status filter. `unit_calculate_height_data` (71) derives walking and total body heights; absent, Dead, Crystal and Treasure units become `UNIT_HEIGHT_UNAVAILABLE`. Ordinary dry unmounted bodies are six half-height units tall: in the baseline, both bodies span walking 20 to total 26. `target_validate_height_overlap` (target_panels, 1423) requires:

`target.walking < actor.total && target.total >= actor.walking`.

The strict/inclusive asymmetry is source behavior. Both comparisons pass for 20..26. A normal Dead target fails the body-height path before formula dispatch, although later `action_finalize_target_result` also cancels Dead/Petrify/Wall targets if they reach it. Do not call that later cancellation a pre-formula no-draw check.

`target_list_units_on_panels` (action_preparation, 1001) gathers active, targetable marked units; the selected one-target scenario has no ordering ambiguity. `action_prepare` (190) validates actor and, for unit-target commands, target slot/activity; its Attack branch copies the command, sets ability ID 0, marks action taken in commit phase, and returns immediate. **That branch itself does not validate range or action availability.** UI selection/range marking, target marking, preparation and execution are distinct steps. A managed headless command must enforce their intended combination explicitly, without assuming the formula is a safe public validation entry point.

Recommended atomic API gate: require current actor turn, action unused, supported configuration, valid/current unit IDs, active living nonself target on an in-range tile, body overlap and targetable terrain; reject before mutating state or drawing. This is the chosen synthetic managed command contract, not a claim that every original UI cancellation or every call to `action_prepare` is atomic. Targeting an empty tile can be meaningful in the original flow; the bounded unit-attack API rejects it deliberately and must describe that restriction.

## Facing and hit resolution

`src/battle/action_resolution.c::action_clear_current_data` resets the result to hit=true, accuracy=100, no effects. `action_calculate_target_result` selects `weapon->formula` for Attack, loads weapon and status records, calls `reaction_check_evasion` before dispatch, and dispatches table entry 1 to `src/battle/formula_weapons.c::formula_weapon_damage`. All reacting paths are excluded from this scenario.

The chain is `formula_evade_calculate_physical` -> `formula_evade_store_physical`, evade modifiers, weather/facing, `formula_evade_calculate_final_hit_percent`. Base hit is 100; equipment evades are zero and class evade is the supplied 10. `formula_evade_calculate_facing` uses dominant X/Y displacement and target facing. Actor (1,1) to target (2,1): West is front, North/South are side, East is back. Side/back sets class evade=0; back also sets both hand evades=0. Accessory evade remains. There is no generic damage bonus from attacking the back in this chain.

Displayed accuracy is the product of the four truncated per-source percentages: baseline `100*100*100*90 / 1000000 = 90`, then scaled by initial accuracy 100. Actual checks are independent sequential accessory, right hand, left hand, class, with early return on an executing evade. Every zero-evade source still draws. A draw succeeds at evading when `floor(raw*100/32768) < evade`; equality fails the evade. There is no additional aggregate 90% roll. The facing variants retain all four draws even when every evade becomes zero.

The [RNG note](rng-state-and-ordering.md) records the preview exception: direct evade rolls consume draws outside execution while critical uses a midpoint. This attack design measures execution-state inputs at dispatch and does not run UI preview against authoritative managed RNG state.

## Damage arithmetic, result application and KO

`formula_calculate_weapon_damage` -> `formula_calculate_base_xa`: ordinary Sword uses actor PA as XA (5) and weapon power as YA (5). PA and weapon power are unsigned bytes; XA/YA fields in `include/fft/action.h` are signed 16-bit. No weapon-power draw occurs for Sword. Physical modifiers then run in source order: Two Hands/Attack Up/Martial Arts, Berserk/Frog, Defense Up, target physical statuses, zodiac. All are neutral here. Same zodiac sign selects the neutral table entry; no gender-dependent case is needed.

`formula_calculate_critical_hit` rolls scaled raw out of 100 against 4. On critical it adds `floor(rawBonus*baseXA/32768)` to signed 16-bit XA and calls knockback calculation. With XA5, bonus is 0..4; a critical need not increase damage. The target at the east boundary would be pushed to (3,1), outside this map, so `move_knockback_check_destination` rejects that destination and no knockback is queued. This spatial precondition bounds knockback rather than deleting the original critical branch.

`formula_store_xa_times_ya_damage` multiplies promoted signed operands and narrows to signed 16-bit `damage`, stores `ACTION_TYPE_HP_DAMAGE`. Baseline 25 and maximum chosen critical 45 fit. `action_finalize_target_result` caps positive HP/MP changes at `ACTION_VALUE_MAX=999`, cancels knockback/proc for lethal HP damage, and applies target invalidation/Golem logic. Negative signed-16 overflow is **not** generalized into a clamp; this slice supports only products 0..32767. A future expansion must trace target instruction narrowing and negative damage behavior instead of substituting unlimited arithmetic.

`formula_element_modify_weapon_damage` and absorption introduce no effect for element 0/neutral affinities. The 19% added-effect roll still occurs after a hit even for this empty status record. A successful proc may set an added-effect flag, but status application contributes no statuses and preserves hit/accuracy/miss type. Final lethal handling may clear pending proc flags. A future event model should distinguish meaningful simulation events from this source scratch bit.

Result calculation precedes application: `src/battle/action_preparation.c::action_resolve_strike` builds the target list and calls `action_calculate_target_result`; `src/battle/state_actions.c::action_apply_strike_results` invokes `action_apply_target_result` for each computed target. That function (action_resolution, 813) dispatches reactions, returns without HP changes if hit=false, otherwise computes signed 32-bit `oldHP - hpDamage + hpHealing`, clamps below zero and above maxHP, and stores unsigned 16-bit HP. `action_data_t.hp_damage` is signed16 and old HP unsigned16; both promote to signed32 in this subtraction. Our projection excludes all reaction/Golem/damage-sharing/reward mutations that could change these fields. MP remains zero.

At newly zero HP, pending status changes are cleared, Dead is inflicted through `status_resolve_unit_changes`, and execute mode increments unsigned-byte `ko_count`. For nonzero HP <= `maxHP/5` (integer division), Critical status is inflicted; otherwise it is removed. `status_resolve_unit_changes` and status callbacks can have wider consequences in the complete game. This first milestone must represent Dead/KO and Critical coherently; it does not claim full death-countdown, crystal/treasure, revival, battle-victory or reward equivalence. New Dead application is not synonymous with immediately deleting the unit.

## RNG order and executable-generator boundary

Use the verified BIOS policy `nextState = (state*1103515245 + 12345) mod 2^32`, output `(nextState >> 16) & 32767`. The [BIOS report](bios-rng-verification.md) owns its independent instruction evidence and limits. Values below combine that generator with static formula interpretation; the combined attack has not executed against original C.

Execution order is four evade draws until miss; if hit, critical check; if critical, bonus draw; if hit survives element handling, added-effect draw. Thus class miss consumes 4, normal hit 6, critical hit 7. No draws for deterministic Sword base power, damage multiplication, ordinary HP clamp, action-taken marking or turn CT refund. These are bounded-chain counts, excluding preparation previews, unrelated global RNG consumers, rewards, reactions and presentation.

## Action and turn consequences

`src/battle/state_actions.c::action_execute_ability` calls `turn_set_act_taken` and marks the runtime acted flag **before** committing preparation and resolving damage. `action_prepare`'s commit phase also writes action_taken for Attack; Attack returns immediate and spends no charge CT or MP. `unit_facing_turn_to_cursor` turns the attacker toward the target. A miss does not restore the action. A facing-choice/menu phase remains separate from formula execution.

`src/battle/turn_order.c::turn_set_act_taken` -> `turn_set_move_act_taken` sets action_taken=1 and ends the turn only when `turn_should_end` says both movement and action are unavailable. With movement unused/no restrictions, an attack alone leaves movement available and the turn alive. With movement already taken, it ends the turn (even before damage calculation in this source call sequence). Do not always end a turn merely because an attack occurred.

`turn_end` adds20 CT if movement unused and unrestricted, adds20 if action unused and unrestricted, caps at60 and clears has_turn. Start-of-turn processing already replaced CT with excess `%100` (Quick255 is special). For post-start CT0: attack then explicit end without moving yields CT20; move+attack yields CT0; neither used then end yields CT40. For post-start CT50, attack without moving then end caps70 to60. `has_turn=0` for ended cases. The actor's facing should be east after this selected attack. Those lifecycle vectors apply to the scoped ordinary statuses; CT scheduling and action availability remain separate from immutable content.
