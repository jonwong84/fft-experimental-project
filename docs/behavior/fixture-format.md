# Behavioral fixtures v1 (ZOD-002)

Date: 2026-10-22. This defines the fixture data contract; [ZOD-011's test runner](fixture-runner.md) now executes the bounded managed scenarios. No production serialization API is introduced. FFT owns these fixtures under `Fft.*`; they do not become Zodiac engine contracts. The [ownership audit](../architecture/zod-001-type-ownership.md) remains the extraction plan.

## Files and versioning

Store committed, synthetic scenario data and provenance in `docs/fixtures/behavior/*.json`. The format is identified by `format: "fft.behavior-fixture"` and integer `schemaVersion: 1`; this distinguishes it from the existing sprite decode fixture, whose unrelated version is also 1. A reader must reject an unknown format/version, duplicate JSON keys, unknown fields, missing required fields, invalid enum strings, invalid IDs and non-integer numeric values. Do not silently fill absent state fields from current constructors. A schema change needs an explicit version and migration decision; changing only provenance or correcting expectations does not change the schema version, but must be explained in review.

The [synthetic accepted move](../fixtures/behavior/flat-move.synthetic.json) and [rejection replay](../fixtures/behavior/flat-rejections.synthetic.json) are executable transition examples. The [source-traced boundary description](../fixtures/behavior/map-boundary.source-description.json) uses the same envelope with `execution: "description-only"`; it specifies direct coordinate-guard vectors and a separately labeled managed transition projection. Description-only records are validated and reported as not executed, never as runner passes.

## Envelope and evidence

Every file requires these fields:

- `fixtureId`: unique, stable namespaced ID, following the current `AssetId` lowercase ASCII grammar. Filenames, unit display names and array indices are not identity.
- `execution`: `scenario` or `description-only`; `purpose`: the bounded claim; `target`: game, edition, region, platform and policy ID. `SCUS-94221` identifies the compatibility target, not proof that a synthetic scenario occurred on that release. Prototype policy IDs must say prototype; do not label the current flat transition as the PS1 movement implementation.
- `reference`: observed local decomp full SHA-1 and observation date. Record it even for a synthetic example, with `usedForExpectations: false` when appropriate. This is source identity, not an assertion of source-derived results.
- `evidence`: uniquely named entries containing `id`, `kind`, `confidence`, `claim`, `sources`, and `limitations`. Kinds are `synthetic-expectation`, `source-derived`, `executable-reference`, and `original-observation`. Confidence is `specified`, `source-traced`, `independently-observed`, or `unresolved`. Synthetic evidence uses `specified`; static source evidence uses `source-traced`. Executable/original observation may use `independently-observed` only with a reproducible record. Confidence is scoped to the stated claim, not to the entire fixture.
- `preconditions`, `exclusions`, and `unknowns`: explicit string arrays. Use empty arrays when none exist, never an invented expected value for an unknown.
- `scenario`: full synthetic initial state and ordered commands, or null for a description with no managed projection. `sourceCases`: direct function inputs/outputs, or an empty array. `expectations`: ordered expected transition snapshots, or empty when there is no managed projection. `captures`: local evidence metadata, or empty if nothing was captured.

Every source entry has `path`, `symbol`, and `revision`. A decomp entry uses a repository-relative C path, function name and the full decomp SHA; managed entries use a repository-relative path, symbol and repository commit. Paths plus revision plus symbol are authoritative; optional line numbers in prose are navigation aids. Inspect callers before describing a function output as a game outcome. An executable-reference entry must also describe the harness revision, compiler/options, input preparation and output capture; executing a separate transcription is not executing the original C routine. An original-observation entry must describe edition/hash verification, emulator/hardware version, setup and capture procedure. Add those details in its limitations/claim or a linked committed note, and reference capture metadata.

Each source case and each expected assertion group requires `evidenceIds`. IDs must resolve locally and support exactly that group. A source trace supporting coordinate rejection does not support a typed C# rejection code or event order. Keep those as a synthetic group. `unresolved` evidence is research metadata only: no assertion may cite it as its sole justification or count it as a verified result. A reader must fail fixture validation for such an assertion rather than silently accepting it. Unresolved claims belong in `unknowns` until supported.

## Bounded scenario payload

V1 scenarios target `BattleSimulator.Apply` with flat prototype movement only. `scenario.initialState.map` contains a stable `id`, positive integer `width`, `depth`, `layerCount`, and an explicit `tiles` array in layer/Y/X order (X fastest), exactly width * depth * layers entries. Each tile includes surface ID, height, halfHeight, waterDepth, slope (east/west/south/north), ceilingDepth, and symbolic movementFlags. These are synthetic managed values, not packed disc bytes.

`initialState.units` is an ordered array with unique stable IDs, position (x/y/layer), hasMoved, and a full movementProfile: move, jump, bodyHeight, mode, traits and terrainCosts. Terrain costs are objects with surface ID, movePoints and isBlocked, unique by surface ID. Empty costs are explicit for the flat prototype. Symbols match the current managed enums exactly. Positions must be in bounds; do not add an initial occupancy restriction absent from current `BattleState`. `rngState: null` explicitly records that this transition has no RNG. Future RNG behavior requires a defined state/width/draw comparison extension before use.

Commands are ordered objects with contiguous integer `index` starting at zero, `kind: "move-unit"`, unitId and destination. Each command applies to the previous returned state, including after rejection. Inputs must be valid constructor data; malformed-fixture validation is distinct from a legal command rejected by simulation.

Each `expectations` entry has a matching commandIndex and `assertions` array. V1 assertion groups use either `{ "kind": "result", "accepted", "rejection", "evidenceIds" }` or `{ "kind": "state-and-events", "stateRelation", "state", "events", "evidenceIds" }`. Every scenario command needs exactly one of each group. `stateRelation` is `same-instance` for rejected or `new-instance` for accepted transitions. It is a managed identity check against the preceding state, not persisted object identity.

The expected `state` is `{ "mapId", "units", "rngState" }`; units contain every field defined above. The mapId resolves to the immutable initial map; compare map dimensions and every tile with the initial map as well as its logical ID. Events are an ordered array of `{ kind: "unit-moved", unitId, from, to }`. All other event shapes are unsupported in v1. A description may provide these same groups without claiming execution. Source cases use `{ id, function, inputs, expectedReturn, evidenceIds }`, with named integer inputs specific to that function; they are research vectors, not a C runtime dependency.

## Comparison and reporting

Compare every command in order, then accepted/rejection, stateRelation, map fields, ordered units and all their explicit fields, RNG state, then ordered events and their fields. Exact ordinal, case-sensitive stable IDs must match; resolve IDs explicitly, without hashes or fuzzy names. Unit list order is observable and must match, even when the same units exist. Compare symbolic flag sets without order, reject duplicates/unknown flags; compare terrain-cost entries by surface ID without order. JSON object property order has no meaning. Any missing, extra or duplicated event fails; never sort events to obtain a pass.

All v1 numeric simulation fields are signed 32-bit integers with exact equality, no tolerance, culture-dependent formatting, fractional values or numeric strings. Enforce field constraints of the managed inputs (including two-bit slope edges); do not narrow them to original packed widths unless an import/source case explicitly requires that width. The boundary source cases use signed `s32` x/y and positive map dimensions. Rejected commands must leave all projected fields unchanged and emit zero events; accepted examples must leave the input snapshot unchanged as a separate managed invariant. No unlisted field is implicitly allowed to drift.

Report fixture ID, policy, command index, evidence kind/confidence and the first differing field path with expected/actual values, for example `expectations[0].state.units[0].position.x`. Distinguish invalid fixture, failed assertion, not executed and passed assertion. Describe synthetic passes as prototype regressions; source-derived passes as invariant checks against static analysis. Neither is original-game equivalence. Record the implementation commit in run output, separately from the reference commit; a changed reference does not automatically rewrite expected results. Re-trace affected claims deliberately.

Do not persist `GetHashCode`, `HashCode`, dictionary/set iteration, or serialized .NET object graphs as replay fingerprints. V1 compares explicit values and defines no persistent fingerprint. If a later cache needs one, specify canonical bytes and a named cryptographic algorithm in a separate versioned contract. Range sets, if added later, must be compared by membership rather than enumeration.

## Captures and validation boundary

Keep BINs, extracted files, decoded media, emulator saves, screenshots and oracle outputs under ignored `scratch/behavior/<fixture-id-safe-folder>/`. Commit only metadata. Each actual capture entry must contain a stable capture ID, kind, repository-relative localPath under `scratch/`, SHA-256 of the raw file bytes, byteLength, tool/version, procedure note and edition-verification note. Reject rooted paths, traversal and paths outside scratch. Do not insert fictional hashes or capture entries for work not performed. These examples have no captures and do not require a BIN hash because they contain only synthetic data and static source study.

Missing local captures must report unavailable evidence, never fabricated verification. The baseline runner must run committed synthetic scenarios without loading captures, BINs, C code, network, renderer or emulator. Capture-dependent differential checks are separately selected local checks. The existing sprite fixture is not silently upgraded or reclassified by this design.

Original design validation consisted of JSON parsing, link and evidence-reference checks, hand-checking complete prototype snapshots against the managed transition, and re-reading the pinned coordinate guard and its caller. Subsequent ZOD-011 implementation executes the synthetic scenarios and tests deliberate mismatches and invalid input; see [runner checks and limits](fixture-runner.md).
