# Variable supported-list search and turns — ZOD-265–270

Design extension, 2026-11-04, managed base `1136eec`; read-only fft_decomp
checked clean at `11464943bbdbd2a0af022d90cb7f10455cf911df`.
The [ZOD-264 study](zod-264-variable-action-lists.md) owns list/occurrence,
ranking and terminal-context evidence. The
[extended source receipt](../evidence/ai/variable-search-source-v1.json) adds
the existing complete-turn/controller/clock boundaries from ZOD-247. No original
or C execution; no general learning, menu, map, roster or policy port.

The selected incremental milestones are:

- **ZOD-265:** separate pure before/after-ACT preparation for owned supported
  lists, with occurrence provenance, asymmetric peer threats, correct support
  clearing, grant inclusion rather than inferred grant absence, and one refresh.
  Existing canonical preparation and its list guard stay intact.
- **ZOD-266:** derive variable-list movement scenarios through the shared
  `AiMovementScenarios` owner. Stone presence determines the ranged D0 floor;
  keep source masks, actor insertion and fresh versus unwritten priority facts.
  No action search or public cached prefix input.
- **ZOD-267:** compose present usable occurrences in source order, preserving
  repeated self coins/clocks and repeated Stone aim scans/rank admissions. Use
  the existing Attack/self/Stone entry and insertion owners. Resolve cast keys
  only for present damage actions: range1 without Stone, range4 with it. Unknown
  readable keys reject, while unused actions cannot trigger grants or scans.
  Return per-occurrence diagnostics and last entered usable command kind without
  fabricating absent legacy entry outcomes.
- **ZOD-268:** reuse the ranked lottery with occurrence identity. Derive terminal
  context from owned traversal, retaining NoDefend/ordinary-default facts but
  requiring no false TerminalThrowStone assertion. Failed queries restore RNG
  and priority knowledge as one transaction.
- **ZOD-269:** privately own fresh variable selection inside Framework's existing
  callback, sharing typed dispatch/proposal construction with canonical entry.
  No new public callback, cached executable plan, friend access or authority.
- **ZOD-270:** complete variable-list turns from actual results, including one
  post-ACT preparation/scenario/empty selection through the same new owners.
  Reuse actual continuations/facing and stage/recovery mechanics, preserving
  accepted knowledge, effects and RNG. Exact-session retry only the failed stage;
  terminal encounter routing and next-turn clocks remain excluded.

New list APIs carry separate diagnostics and typed results; they must not
construct fake canonical lists, pair certificates or missing self/Stone outcomes
to pass old guards. Remaining ordinary source-context facts stay explicit.
Preparation admits original-compatible extents only; catalogs remain unbounded
by original storage constants. A repeated gameplay ability needs one executable
grant but multiple evaluated occurrences. An unlisted AI action may still have
a valid gameplay grant.

Use literal missing/reordered/duplicate action tapes, parity with canonical
queries and original isolated descriptions, absence of grants for unused
actions, range1 versus4 priority reads, exact/late budgets, both teams/actors,
actual self/Attack/Stone/empty turns and recovery. Preserve all old APIs/streams,
immutable inputs and owner definition drafts. Host/editor activation, broad
replacement interfaces, frame/VSync RNG and ZOD-106 remain deferred.

All six milestones are implemented and validated in the
[behavior and validation report](../behavior/variable-basic-skill-ai.md).
